ランニングフォーム比較アプリ RunGap 開発案
作成日：2026-07-16　版：v0.10（最終更新：2026-07-28）

[** 一言でいうと]
 使用者の体型を反映した[3Dモデル]に「理想の走り」をさせ、実際の走行動画と比較して、どの部位がどれだけ数値的に離れているかを提示する[Webアプリ]。

[** 設計思想（最重要）]
 [* 「正解を押し付けない計測器」であること]
 アプリの役割は理想と現実の差分を数値で提示するところまで
 数値を改善に取り入れるかどうかは選手・指導者本人の判断に完全に委ねる
 評価・採点・ランク付け機能は意図的に搭載しない
 UI文言でも「診断」「判定」「スコア」「改善点」という語は使用禁止 →「比較」「差分」「数値」「記録」に統一

[** 対象ユーザー]
 主対象：愛知工業大学 陸上競技部 長距離ブロックの競技者
 副対象：同ブロックの指導者（選手との対話材料として使用）
 収益モデル：無料（部内ツールとして運用）

[** 利用の流れ]
 1. 陸上競技トラック400mのゴール付近にスマホ1台を設置して走行を撮影（側方・真横から）
 2. 練習後に動画をアップロード（事後解析型）
 3. 登録済みの「理想の走り」と比較を実行（約2〜3分）
 4. 部位ごとの差分数値と3D並走再生を確認
 5. 取り入れるかは本人が判断する

[** コア機能（Phase 1）]
 [* F1 体型入力・3Dモデル生成]
  数値入力：身長・体重・骨格筋率・体脂肪率・股下長（必須）＋座高・上腕長・肩幅・足長（任意）
  パラメトリック人体モデルを変形して使用者のボディラインを近似再現
  骨格筋率→四肢・肩周りのボリューム、体脂肪率→胴回り・丸みに反映
 [* F2 理想モーション登録]
  お手本動画（プロ選手・チームメイト・過去の自分）からモーションを抽出
  使用者の体型のアバターに角度ベースでリターゲット（体格差による破綻を防ぐ）
  物理的整合性チェック付き（接地貫通・可動域超過・ペース不整合を検査）
  複数登録・名前管理が可能
 [* F3 環境条件入力]
  現実で走る時と変わらない環境をシミュレーションに反映
  入力項目：風速・風向・気温・路面傾斜・路面種別・目標ペース
  [* 風の扱い]（400mトラック周回モデル前提）
   アバターはトラックを周回するため、1周する間に同じ風でも追い風・向かい風・横風のすべてを受ける
   風は「トラックに対して固定された1本のベクトル」として扱う
   風速：ベクトルの大きさ（km/h・符号なし。追い風＋/向かい風−のような符号は使わない）
   風向：ホームストレートを基準に「追い風／向かい風／横風・右／横風・左」を選択
   → 大きさ（風速）と向き（風向）を分担して指定するので情報は重複しない
  重力・空気密度・体重慣性はアプリ側で自動設定
  「いつものトラック」プリセットで通常は風（風速・風向）とペースの入力のみ
 [* F4 走行動画アップロード・解析]
  スマホカメラ1台・側方撮影が標準
  撮影ガイド常設（高さ1.0〜1.5m・走路から10〜15m・60fps推奨）
  サーバー側で3D姿勢推定 → 歩行周期検出 → 指標算出
 [* F5 差分比較・数値提示（核心機能）]
  1歩行周期で正規化し、接地・立脚中期・離地・遊脚中期の局面同士で比較
  比較指標と差分の単位
   膝関節角度：度（°）局面別
   体幹前傾角：度（°）
   腕振り角度：度（°）振り幅
   接地時間：ミリ秒（ms）左右それぞれ
   ストライド長：センチメートル（cm）
   ピッチ：歩/分（spm）
  [* 接地時間の左右計測の注意]
   側方単眼1台では手前脚が奥脚を遮蔽（オクルージョン）するため、奥側脚のタイミング推定が不安定になりやすい
   単一の1歩で確定せず複数歩から統計推定し、左右で信頼度が異なる場合がある旨を明示
   奥側脚など遮蔽の影響が大きい値には低めの信頼度を表示
   左右差を主目的とする計測は将来の後方・前方カメラ追加がより適する
  [* ストライド長など絶対長（cm）の較正]
   単眼映像には絶対的な長さ情報がないため、F1入力の身体寸法（身長・股下長）を3D骨格に当てて画素↔実長のスケールを求めてcm換算する
   → cm精度は体型入力値と骨格スケール推定の精度に依存する
  提示形式：「理想値／あなたの走り／差」の3点セット、評価語なし
  各指標に推定信頼度（高・中・低）を併記して精度の限界を隠さない
 [* F6 3D並走ビューア]
  重ね表示モード（半透明の理想＋実体の実走）と並走表示モード
  スロー再生・1フレーム送り・局面ジャンプ・自由カメラ
 [* F7 履歴管理]
  差分の推移を折れ線グラフで閲覧、自由記述メモ付き

[** 技術構成]
 3Dエンジン：[Unity]（WebGLビルドとしてWebに埋め込み）
 姿勢推定：サーバー側GPUで機械学習モデル（Phase 0で4系統を比較選定）
  候補4系統：①RTMPose／MMPose系（軽量2D検出）、②ViTPose系（高精度2D）→①②は2D→3D積み上げ型、③人体メッシュ復元型（SMPL系・CameraHMR等）、④拡散・フローマッチング系（FMPose3D等）
 解析の場所：[* サーバー処理を採用]
  理由：単眼動画の高精度3D推定には重いモデルが必要／端末差の影響を受けない／開発・改良が容易
  対象が1チーム規模のためサーバーコストは小さい
  将来のリアルタイム型は端末内軽量推定＋サーバー精密解析のハイブリッド構成へ
 サーバー調達：[* 大学研究室のGPUサーバー（オンプレミス）を採用]（クラウドGPUは不採用）
  理由：体組成・動画を学外に出さずに扱えプライバシー・同意面の負担が小さい
  開発初期はローカルサーバー（開発機）で構築・検証 → 研究室GPUサーバーへ移行
  運用開始時は初期利用者を2〜3名に限定し段階的に拡大
 バックエンド：Python（FastAPI等）＋ジョブキュー
 プライバシー：動画原本は解析後30日で自動削除、体組成データは本人と許可した指導者のみ閲覧可

[** 開発フェーズ]
 Phase 0（2〜3ヶ月）：単眼姿勢推定の精度検証 ← 最大のリスクを最初に潰す
  精度の基準（参照値）：Sony mocopi（関節角度）＋Garmin/Corosのランニングダイナミクス（接地時間・ピッチ・ストライド長・接地時間の左右バランス）を同時計測。両者とも推定値のため真値ではなく「複数推定の一致度」で検証
  判断基準例：膝関節角度差±5°以内、接地時間差±20ms以内
 Phase 1（4〜6ヶ月）：Webアプリ初版（F1〜F7、事後解析・手動体型入力）
  開発初期はローカルサーバーで構築→研究室GPUサーバーへ移行、初期利用者2〜3名限定で試験運用
 Phase 2（2〜3ヶ月）：指導者共有・履歴グラフ拡充
 Phase 3（時期未定）：写真自動採寸／リアルタイム型／iOS・Androidネイティブ対応

[** 主なリスク]
 単眼推定の精度不足 → Phase 0で最初に検証、信頼度表示で限界を明示
 屋外撮影条件のばらつき → 自動品質チェック＋撮影ガイド
 体格差リターゲットの破綻 → 角度ベース転写＋整合性チェック＋警告
 数値の独り歩き（差分＝悪という誤解） → UI文言規則と指標解説で防ぐ
